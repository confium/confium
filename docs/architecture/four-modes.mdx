# Four deployment modes

Confium's threshold cryptography can be deployed four different
ways. Each mode targets a different operational model. Picking the
right mode for your use case is the most important early design
decision.

| Mode | Persistent keys? | Share ops? | Identity-bound? | PKI integration? | Operational cost |
|---|---|---|---|---|---|
| **1. Peer-to-Peer TC** | Yes | Yes | No | None | Medium |
| **2. PKI Drop-in** | Yes | Yes | No | Drop-in | Medium-High |
| **3. Sovereign PKI** | Yes | Yes | No | Custom format | Very High |
| **4. Keyless Threshold** | **No** | **No** | **Yes (OIDC)** | **Fulcio-style** | **Low** |

## Mode 1 — Peer-to-Peer TC

Nodes do threshold cryptography directly, no PKI required. The
threshold keyset is persistent and managed by the node operators.

**Best for**: real-time signing networks, blockchain anchor networks,
multi-party computation networks where nodes already trust each
other's operational security.

**Avoid for**: anything where the same keyset has to verify against
existing PKI (TLS, code signing, X.509).

## Mode 2 — PKI Drop-in

Replace single-party keys with threshold keys in an existing PKI
without changing anything else. The threshold joint public key is
embedded in a standard X.509 cert; the cert chain validates
normally; existing verifiers don't know threshold signing is
happening.

**Best for**: enterprise CAs, document-signing infrastructure, TLS
certificate issuance. You get threshold guarantees without
re-issuing every cert or updating every verifier.

**Avoid for**: deployments that need custom certificate formats
(see Mode 3) or where key management is operationally too costly
(see Mode 4).

## Mode 3 — Sovereign PKI

Custom certificate formats and workflows for institutions that
can't or won't use the existing PKI. CNML (Certificate of
Conformity for Measuring Instruments) is the flagship example —
the format is defined by OIML, not by IETF, and the signing
workflow involves accreditation bodies, calibration labs, and
issuing authorities in a quorum.

**Best for**: institutional PKI where the certificate format
itself is domain-specific. Government archives, accreditation
bodies, treaty organizations, BIPM calibration chains.

**Avoid for**: anything where the existing PKI can do the job —
Mode 3 is significantly more work than Mode 2.

## Mode 4 — Keyless Threshold (NEW)

Ephemeral per-ceremony threshold quorums, OIDC-verified signers,
Fulcio-style short-lived certs binding OIDC identities to the
joint ephemeral key, transparency-log anchoring. **No persistent
keys, no share management.**

**Best for**: CI/CD release pipelines, package publishing,
anywhere that "this was signed by these N specific people at this
specific time" is more useful than "this was signed by the
long-lived publisher key". Generalizes the Sigstore keyless
pattern to threshold signing.

**Avoid for**: long-term archival (the Fulcio cert expires in ~10
minutes), regulatory key escrow (you need to be able to re-sign
with the same key years from now), high-throughput signing
(ephemeral DKG adds ~10ms per ceremony).

See the [Mode 4 design doc](./mode-4-keyless-threshold.mdx) for
the full architecture.

## How to choose

Ask:

1. **Do I need the joint key to validate against existing PKI?**
   - **No** → Mode 1 or Mode 4
   - **Yes, with standard certs** → Mode 2
   - **Yes, with custom certs** → Mode 3

2. **Can I afford persistent share management?**
   - **No** → Mode 4
   - **Yes** → any mode

3. **Do signers have OIDC identities (GitHub, Google, Okta)?**
   - **Yes, and identity is the right trust anchor** → Mode 4
   - **No, or key-based trust is required** → Modes 1–3

4. **Is the signing ceremony one-shot or repeated with the same key?**
   - **One-shot per release** → Mode 4
   - **Repeated, same key for years** → Modes 1–3

## Comparison table

| Property | Mode 1 | Mode 2 | Mode 3 | Mode 4 |
|---|---|---|---|---|
| Persistent key | Yes | Yes | Yes | **No** |
| Share management | Required | Required | Required | **Not needed** |
| Identity-bound | No | No | No | **Yes (OIDC)** |
| Long-term archival | Possible | Possible | Possible | **No** |
| PKI integration | None | Drop-in | Custom | Fulcio-style |
| Transparency log required | Optional | Optional | Optional | **Required** |
| Trust anchor | Threshold keyset | Existing CA | Custom CA | Fulcio + log + OIDC |
| Best example | P2P signing networks | Enterprise PKI | CNML | CI/CD release signing |
